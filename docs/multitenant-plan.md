# خطة تحويل نقطة البيع إلى نظام متعدد المتاجر (Multi-Tenant)

> هذه خطة فقط ولن يُنفَّذ منها شيء. التنفيذ يبدأ بعد إجابتك على أسئلة القسم 11.

**المصطلحات المستخدمة في الخطة وفي الواجهات:**
- **متجر:** هو ما سمّيته «يوزر». كل متجر نظام مستقل كامل، له قاعدة بيانات خاصة وعنوان فرعي خاص وحساب دخول لصاحبه.
- **حساب دخول:** اسم مستخدم وكلمة مرور داخل متجر واحد.
- **لوحة الإدارة:** لوحتك أنت، ومنها تنشئ المتاجر وتديرها.

---

## 1. الهدف والنتيجة النهائية

بعد التنفيذ تستطيع أن:
- تدخل إلى لوحة إدارة خاصة بك على `admin.pos.108-61-190-4.sslip.io`، بكلمة مرور ورمز تحقق من تطبيق على هاتفك.
- تنشئ متجرًا جديدًا بكتابة اسمه وعنوانه فقط. يُنشأ له تلقائيًا:
  - قاعدة بيانات فارغة مستقلة،
  - عنوان فرعي عليه شهادة HTTPS،
  - قسم افتراضي اسمه «عام»،
  - حساب دخول لصاحبه.
- توقف أي متجر مؤقتًا ثم تستأنفه، وتعيد تعيين كلمة مرور صاحبه، وترى حجم بياناته وآخر نشاط فيه، وتراجع سجلًا بكل ما فعلته في اللوحة.
- لاحقًا: تحذف متجرًا مع نسخة احتياطية ومهلة تراجع 30 يومًا، وتستعيد نسخة احتياطية، وتغيّر عنوان متجر، وتصدّر بياناته.

الحسابات المدققة تبقى كما هي في كل متجر: التقريب، وتعديلات المخزون، والتقارير حسب حركة المال، وصافي الربح. ولا يرى أي متجر بيانات متجر آخر.

**مثال:** تنشئ «متجر الأمل» بالعنوان `amal`. خلال دقيقتين تقريبًا يصبح `https://amal.pos.108-61-190-4.sslip.io` جاهزًا بقاعدة بيانات خاصة اسمها `pos_t_6650f1c2…`. تنسخ العنوان واسم المستخدم وكلمة المرور المؤقتة وترسلها لصاحب المتجر عبر واتساب، وعند أول دخول يُطلب منه تغيير كلمة المرور. بعد شراء نطاق حقيقي يصبح العنوان `amal.<نطاقك>`.

**قيد أساسي:** على خادمك الحالي المشترك مع المواقع الأخرى تعمل المنظومة لمتجرك وللمتاجر التجريبية فقط. بيع النظام لمتاجر خارجية مشروط بالمرحلة 8: نطاق حقيقي، وخادم مستقل لقاعدة بيانات تعمل بمصادقة. الأسباب في القسمين 6 و7.

## 3. شكل النظام

```
 shop browser                         owner browser
 amal.pos.<ip>.sslip.io               admin.pos.<ip>.sslip.io
        | HTTPS                              | HTTPS + basic auth
        v                                    v
 +--------- nginx  (new file sites-available/pos, niura untouched) --------+
 |  map $ssl_server_name -> /etc/nginx/pos-certs/<host>/                   |
 |  limit_req / limit_conn per host, auth endpoints throttled              |
 +-----------------------------------+-------------------------------------+
                                     v  127.0.0.1:3401
 +------------- pos.service  (Node 24, user pos, systemd) -----------------+
 |  Host == ADMIN_HOST -> admin UI + /api/admin                            |
 |  Host == <slug>.pos -> registry -> status -> session -> req.models      |
 |  job runner ---- writes requests ----+                                  |
 +--------+-----------------------------+----------------------------------+
          | one pool (10)               v /var/lib/pos-spool (desired, requests, state)
 +--------v---------------------+   +-----------------------------------------+
 | MongoDB 8 (shared)           |<--| pos-root-worker (root, timer 1 min)     |
 |  pos_control                 |   |  certbot --config-dir /etc/letsencrypt-pos|
 |  pos_t_<id1> pos_t_<id2> ... |   |  mongodump / mongorestore / drop         |
 |  (hishin/lapsa/niura DBs:    |   |  nightly dumps -> /var/backups/pos       |
 |   never touched)             |   |  -> restic off-site                      |
 +------------------------------+   +-----------------------------------------+
```

## 4. نموذج البيانات

### قاعدة التحكم `pos_control`

| المجموعة | الحقول الأساسية | الفهارس والملاحظات |
|---|---|---|
| `tenants` | `slug`، `label` (اسم المتجر عندك، تراه أنت فقط)، `dbName`، `previousDbNames[{name, dropAfter}]`، `status`، `statusReason`، `statusChangedAt/By`، `contact{person, phone}`، `notes`، `shopNameCache`، `usage{salesCount, productsCount, dataBytes, lastSaleAt, measuredAt}`، `lastActivityAt`، `schemaVersion`، `deletion{requestedAt, requestedBy, purgeAfter, backupFile}`، `rev`، `createRequestId` | فهارس فريدة على `slug` و`dbName`، وفهرس فريد متفرق على `createRequestId` حتى لا يتكرر الإنشاء. `dbName` لا يتغير إلا عبر `switchDb()` في عملية الاستعادة. `rev` رقم يزيد مع كل كتابة |
| `hosts` | `_id` = اسم المضيف الكامل، `tenantId`، `kind: primary/redirect/retired`، `redirectUntil`، `cert{status, attempts, expiresAt, lastError}` | السجل وأداة التحقق من العناوين يقرآن هذه المجموعة. حقل `cert` مجرد نسخة عرض من ملفات حالة العامل. الاسم `retired` محجوز للأبد |
| `admins` | `username`، `passwordHash` (Argon2id)، `totp{secretEnc, enabledAt, lastCounter}`، `recoveryCodes` (مُهشَّرة) | تُنشأ من سطر الأوامر فقط |
| `sessions` | `_id` = SHA-256 للكوكي، `kind: tenant/admin`، `tenantId`، `userId`، `authVersion`، `csrf`، `createdAt`، `lastSeenAt`، `expiresAt`، `ip`، `ua`، `stepUpAt` | فهرس TTL على `expiresAt`، وفهرس على `tenantId` حتى يُلغى متجر كامل بـ `deleteMany` واحد |
| `loginAttempts` | المفتاح `(tenant, username, ip)`، `count`، `lockedUntil` | فهرس TTL |
| `auditLog` | `at`، `actor`، `ip`، `action`، `tenantId`، `tenantSlug`، `details` (بلا أسرار)، `result`، `prevHash` | لا يوجد في الكود أي مسار يعدّل السجل أو يحذف منه، وكل سجل مربوط بسابقه بالهاش. يُحفظ 400 يوم |
| `jobs` | `type: provision/backup/restore/rename/purge/usage`، `tenantId`، `status`، `active`، `steps[{key, status, at, error}]`، `attempts`، `leaseUntil`، `requestId` | فهرس فريد جزئي على `{tenantId}` عندما `active:true`، أي مهمة نشطة واحدة لكل متجر. نفس نمط الجرد المفتوح الوحيد اليوم |

### قاعدة كل متجر `pos_t_<id>`
- المجموعات التسع الحالية تبقى بنفس أسمائها: `categories`، `products`، `counters`، `sales`، `expenses`، `customers`، `debtentries`، `purchases`، `stockcounts`. لذلك تُستعاد أي نسخة قديمة كما هي.
- مجموعة جديدة `users`، وفيها: `usernameLower` (فريد)، `displayName`، `role` (`owner` الآن)، `passwordHash`، `mustChangePassword`، `authVersion`، `disabledAt`، `lastLoginAt`، `passwordChangedAt`.
- مجموعة جديدة `settings` فيها وثيقة واحدة `_id:'shop'`، وفيها: `shopName` (60 حرفًا كحد أقصى)، `receiptNote` (120 حرفًا كحد أقصى)، `timeZone` (افتراضيًا `Asia/Baghdad`)، `currency` (افتراضيًا `د.ع`، وهي تسمية للعرض فقط)، `phone`، `address`.
- حقل جديد `clientId` بفهرس فريد متفرق في `Sale` و`Purchase` وفي سطور المرتجعات. هذا يمنع تسجيل البيع مرتين عند إعادة المحاولة، ولا يغيّر أي حساب.

## 5. التغييرات في التطبيق

| الملف | التغيير |
|---|---|
| `server.js` | يُقسَم إلى `app.js` الذي يصدّر `createApp({registry, db})`، و`server.js` الذي يتصل ثم يستمع. تُركَّب `/healthz` و`/readyz` قبل توزيع الطلبات حسب `Host`، ولا تجيبان إلا إذا كان `Host` هو `localhost` أو `127.0.0.1`. تُغلَق العملية بهدوء عند `SIGTERM` |
| `lib/config.js` و`.env.example` | المتغيرات `MONGODB_URI` (بلا اسم قاعدة)، `CONTROL_DB`، `TENANT_DB_PREFIX=pos_t_`، `TENANT_BASE_DOMAINS` (قائمة، لتسهيل الانتقال لاحقًا)، `ADMIN_HOST`، `PUBLIC_SCHEME`، `MAX_TENANTS`، `MAX_NEW_TENANTS_PER_DAY`، `TOTP_KEY`، `SPOOL_DIR`. القيمة الافتراضية لـ `HOST` تصبح `127.0.0.1`، وفي الإنتاج يرفض التطبيق البدء إذا لم يكن `HOST` عنوان loopback (اليوم القيمة `undefined`، أي الاستماع على كل الواجهات) |
| `lib/db.js` (جديد) | `createConnection` واحد بالخيارات `maxPoolSize:10` و`waitQueueTimeoutMS:2000`، ومنه `control = base.useDb(CONTROL_DB)`، والدالة `tenantModels(tenant)` التي تستخدم `useDb(dbName,{useCache:true})` ثم `init()`. إذا فشل `init()` يبقى المدخل كما هو وتُعاد المحاولة بتأخير متزايد، دون إنشاء اتصال جديد. `assertDbName()` تتحقق من `^pos_t_[0-9a-f]{24}$` قبل أي `useDb` |
| `models/*.js` | كل ملف يصدّر المخطط (schema) بدل النموذج. `nextSequence` تصبح دالة ثابتة `Counter.next(name)`. الدوال الثابتة الأخرى (`valuation`، `owedToSuppliers`، `balanceOf`، `totals`) تعمل كما هي لأنها تستخدم `this` |
| `models/index.js` (جديد) | `SCHEMAS` و`bindModels(conn)`، مع خطّافات `pre(/^find\|^count\|^aggregate/)` تضع `maxTimeMS` بقيمة 5 ثوانٍ، و15 ثانية للتقارير |
| `models/User.js` و`models/Setting.js` (جديدان) | حسب القسم 4 |
| `control/models/*` | `Tenant` و`Host` و`Admin` و`Session` و`LoginAttempt` و`AuditLog` و`Job`، وتُبنى على `control` فقط. لا يُستدعى `base.model()` أبدًا |
| `lib/slug.js` | يقبل `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` بطول 3 إلى 30 حرفًا. يرفض أي نمط عنوان IP بشرطات `\d{1,3}(-\d{1,3}){3}`، وأي مقطع من 8 خانات hex، وأي `--`. فيه قائمة محجوزة واحدة: admin، www، api، app، pos، mail، smtp، ftp، ns1، ns2، static، assets، cdn، media، status، health، help، support، billing، login، auth، root، system، test، dev، staging، demo، localhost، autoconfig، autodiscover، sales، erp، sites، hishin، lapsa، urgold، niura (الاسم `smoke` غير محجوز) |
| `lib/tenancy.js` | الدالة `normalizeHost(req.headers.host)` هي المكان الوحيد الذي يُستخرَج منه المضيف. التوزيع: المضيف الإداري يذهب إلى `adminRouter`. أي مضيف آخر يُبحث عنه في السجل، ثم تُفحص حالة المتجر (قبل فحص الجلسة)، ثم يذهب إلى `tenantRouter` |
| `lib/registry.js` | كل المتاجر والمضيفين في الذاكرة. التحديث فوري عند الكتابة من اللوحة، واستطلاع لحقل `rev > lastRev` كل 5 ثوانٍ (لالتقاط ما يكتبه سطر الأوامر أو العامل)، وإعادة تحميل كاملة كل 5 دقائق |
| `lib/auth.js` و`lib/permissions.js` و`lib/security.js` و`lib/limits.js` و`lib/messages.js` | الجلسات وCSRF، وصلاحيات الأدوار (`owner: ['*']`)، ورؤوس الأمان، وحدود الطلبات المتزامنة لكل متجر، ونصوص الرسائل العربية الموحّدة |
| `routes/*.js` السبعة | لا تستورد أي نموذج بعد الآن. كل معالج يبدأ بـ `const {...} = req.models`، والدوال المساعدة تأخذ النماذج معاملًا أول، مثل `takeFromStock(Product, …)` و`collectedEvents(DebtEntry, end)` و`giveBack(m, purchase)`. البيع والشراء والمرتجع يقبلون `clientId`، وإذا تكرر يُعاد المستند نفسه بالحالة 200. قائمتا المنتجات والمبيعات تحصلان على حد أقصى للنتائج |
| `routes/auth.js` (جديد) | `GET /api/auth/shop` (عام، يعيد اسم المتجر فقط)، `POST /login`، `POST /logout`، `POST /logout-all`، `GET /me` (المستخدم، الدور، `csrf`، `expiresAt`)، `POST /password` |
| `routes/settings.js` و`routes/csp-report.js` | إعدادات المتجر (للمالك فقط)، ونقطة لاستقبال تقارير CSP بحد معدل |
| `admin/` و`admin-public/` | واجهة الإدارة و`/api/admin/*`. لا يُستخدم `innerHTML` مع أي بيانات، و`textContent` فقط |
| `services/tenants.js` | `createTenant` (خطواتها قابلة للتكرار دون أثر جانبي)، و`transition(id, from, to)`، و`switchDb()` |
| `scripts/` | `create-admin.js` (يقرأ كلمة المرور من الطرفية دون إظهارها ويطبع رابط `otpauth`)، `tenant-create.js`، `tenant-purge.js`، `seed.js --tenant`، `bench-tenants.js` |
| `ops/` | `pos-root-worker` و`pos-cert-install` ووحدات systemd. تُراجَع ثم تُنسخ يدويًا إلى `/usr/local/sbin` |
| `public/js/rounding.js` (جديد) | تنفيذ واحد لـ `roundTo` يستورده `lib/util.js` و`common.js` معًا |
| `public/js/common.js` | `api()` يرسل `X-CSRF-Token`. لا ينتقل لصفحة أخرى عند فشل عملية كتابة، بل يرمي خطأً له نوع: `AUTH_EXPIRED` (401)، `TENANT_SUSPENDED` (423)، `TENANT_MOVED` (410). يملأ `.brand-name` ونهاية `document.title` من `/api/auth/shop`، والنص الاحتياطي يبقى «نقطة البيع» |
| `login.html` و`settings.html` (جديدتان) | صفحة الدخول تتبعها صفحة «تغيير كلمة المرور» عند اللزوم، ثم صفحة الإعدادات. في قائمة «المزيد» يُضاف «الإعدادات» و«تسجيل الخروج» مع اسم المستخدم، وشريط القائمة ذو العناصر الخمسة يبقى كما هو |

## 6. الهوية والأمان

**كلمات المرور:**
- الخوارزمية Argon2id بالمعاملات m=19 MiB وt=2 وp=1، وتعمل عمليتا تجزئة على الأكثر في نفس الوقت. يُرفض ما يزيد عن 128 حرفًا قبل التجزئة.
- إن تعذّر تثبيت الحزمة `argon2` على الخادم، يُستخدم `scrypt` من `node:crypto` بالمعاملات N=2^14 وr=8 وp=5.
- كلمة مرور المتجر 10 أحرف على الأقل، ويُسمح بالعربية. تُرفض كلمات المرور الشائعة، وأي كلمة تحتوي اسم المستخدم أو العنوان.
- كلمة مرور المسؤول 14 حرفًا على الأقل، مع TOTP.

**الجلسات:**
- كوكي المتجر `__Host-pos_sid` بالخصائص `Secure` و`HttpOnly` و`SameSite=Lax`، بلا `Domain`.
- كوكي المسؤول `__Host-pos_admin` بـ `SameSite=Strict`.
- في كل طلب يُفحص أن الجلسة من نوع `kind==='tenant'`، وأن `tenantId` يطابق متجر المضيف، وأن `authVersion` يطابق المستخدم.
- مدة المتجر: 72 ساعة خمول، و14 يومًا حدًا مطلقًا، مع تنبيه عندما يبقى أقل من 8 ساعات. مدة المسؤول: 30 دقيقة خمول، و8 ساعات حدًا مطلقًا.
- تغيير كلمة المرور أو إعادة تعيينها يزيد `authVersion`، فتنتهي كل جلسات ذلك المستخدم.
- كل استجابات `/api` تحمل `Cache-Control: no-store`.
- في وضع التطوير فقط تُستخدم أسماء كوكي بلا `__Host-` لأن التطوير يعمل على http.

**الحماية من CSRF، على المتاجر وعلى `/api/admin` معًا:**
- رمز متزامن يُرسل في `X-CSRF-Token`.
- `Origin` يجب أن يساوي تمامًا `PUBLIC_SCHEME://<host>`.
- `Sec-Fetch-Site` يجب أن يكون `same-origin` عندما يُرسل.
- لا تُرسل رؤوس CORS أبدًا، وتبقى مسارات GET بلا أي أثر جانبي.

**محاولات الدخول:**
- يُرفض أي `username` ليس نصًا أو يزيد عن 64 حرفًا بالحالة 400.
- يُفعَّل `sanitizeFilter` على استعلامات الدخول فقط. تفعيله على كل التطبيق يعطّل 19 فلترًا تستخدم `$gte` وأمثالها في `routes/`.
- القفل يكون لكل ثلاثية (متجر، مستخدم، IP): 5 أخطاء خلال 15 دقيقة تقفل 15 دقيقة، وتتضاعف المدة حتى 4 ساعات.
- لكل (متجر، مستخدم) من كل العناوين يوجد إبطاء فقط بلا قفل، والجهاز الموثوق بكوكي موقّع معفى منه. بهذا لا يستطيع أحد قفل صاحب المتجر عمدًا.
- أكثر من 50 خطأ في الساعة على متجر واحد يضيف تأخيرًا ثانيتين لكل محاولة دخول فيه.
- رسالة الخطأ واحدة دائمًا: «اسم المستخدم أو كلمة المرور غير صحيحة»، ويُستخدم هاش وهمي للمستخدم غير الموجود حتى يتساوى زمن الاستجابة.
- المسؤول لا يُقفل نهائيًا: إبطاء، وتنبيه على تلغرام، وفك القفل من سطر الأوامر.

**المسؤول:**
- طبقتان: basic auth في nginx دائمًا، ثم كلمة المرور، ثم TOTP.
- تفاصيل TOTP: وفق RFC 6238، يُقبل فرق خطوة واحدة، ويُمنع إعادة استخدام الرمز. السر مشفّر بـ AES-256-GCM، وهناك 10 رموز احتياطية مُهشَّرة.
- تسجيل TOTP من سطر الأوامر فقط. الدخول يُرفض لأي حساب مسؤول بلا `totp.enabledAt`.
- عدّاد واحد لأخطاء الرمز في الدخول وفي التأكيد الإضافي (step-up). بعد 5 أخطاء تُحذف الجلسة ويُرسل تنبيه.
- التأكيد الإضافي برمز صالح لـ 5 دقائق مطلوب لهذه العمليات: إنشاء متجر، الإيقاف، الحذف، الاستعادة، إعادة تعيين كلمة مرور، إلغاء الجلسات، التصدير، تغيير العنوان.
- لا يوجد انتحال لحساب متجر.

**الرؤوس:**
- `lib/security.js` وحده يضع CSP و`nosniff` و`Referrer-Policy: same-origin` و`Permissions-Policy: camera=(self)` و`X-Frame-Options: DENY` وCOOP/CORP. nginx يضع HSTS فقط.
- في المتاجر: CSP بوضع Report-Only مع `report-uri /api/csp-report` لمدة 7 أيام، ويتحول إلى إلزامي إذا لم تصل أي مخالفة من أجهزتك، بما فيها ماسح الكاميرا.
- في لوحة الإدارة: CSP إلزامي صارم من أول يوم، مع `require-trusted-types-for 'script'`.

**الحدود لكل متجر:**
- 4 طلبات متزامنة على الأكثر. بعدها يُرد بـ 503 مع `Retry-After` ورسالة عربية.
- تقرير واحد لكل متجر في نفس الوقت، و3 تقارير على مستوى العملية كلها.
- حصة مثل 20,000 منتج، تُقاس كل ساعة بـ `dbStats`. تجاوزها يجعل المتجر للقراءة فقط مع رسالة عربية.
- إنشاء المتاجر محدود بـ `MAX_TENANTS=20` و`MAX_NEW_TENANTS_PER_DAY=5`، ولا يُغيَّران إلا من `/etc/pos/pos.env` عبر SSH، مع تنبيه عند كل إنشاء.

**التشغيل بمستخدم غير root:**
- الخدمة تعمل بالمستخدم `pos`.
- الكود في `/srv/pos/releases/<sha>`، مملوك لـ `root:pos` بالصلاحيات 0750، ولا يستطيع `pos` تعديله.
- الأسرار في `/etc/pos/pos.env`، مملوك لـ `root:pos` بالصلاحيات 0640.
- العامل الوحيد الذي يعمل كـ root سكربت مستقل لا يستورد أي شيء من `/srv/pos`. مدخلاته أسماء ملفات تُفحص بالتعبير النمطي وبـ `lstat`، ويُشغِّل البرامج بمصفوفات وسائط دون تمرير عبر shell.

## 7. البنية التحتية على السيرفر

**ما لا يُلمس:** لا تتأثر مواقع hishin وlapsa وniura وsales-accounts وurgold بأي شيء من هذا:
- لا يُعدَّل أي ملف لـ niura، ولا أي تطبيق في pm2 الخاص بـ root، ولا إعدادات `mongod`، ولا `/etc/letsencrypt`، ولا `hishin-backup` إلا بموافقتك (السؤال 5).
- الإضافات كلها جديدة وبأسماء تبدأ بـ `pos`: ملف nginx ومقطع إعداد، وملفا htpasswd، ووحدات `pos.service` و`pos-root-worker.timer` و`pos-backup.timer` و`pos-monitor.timer`، ومجلدات خاصة بها.
- الإجراء الوحيد المشترك هو `systemctl reload nginx`، ويأتي بعد `nginx -t`. وهو ذرّي، أي يُطبَّق كاملًا أو لا يُطبَّق.
- التحقق: قبل كل تغيير وبعده تُقارن حالة HTTP وبصمة الشهادة لكل موقع آخر، و`sha256sum` لملفات niura.

**الدومين وDNS:** الآن يكفي sslip.io بلا أي إعداد. في المرحلة 8:
1. سجلّا `A @` و`A *` يشيران إلى خادم المتاجر.
2. شهادة wildcard عبر DNS-01 برمز API محصور في منطقة النطاق وحدها.
3. سجل `CAA` يحدد حساب Let's Encrypt الخاص بنا.
4. تُضاف قيمة النطاق الجديد إلى `TENANT_BASE_DOMAINS`.

**nginx:** ملف جديد `/etc/nginx/sites-available/pos`، والأسماء كلها تبدأ بـ `pos_`:

```nginx
map $ssl_server_name $pos_cert {
  "~^[a-z][a-z0-9-]{1,28}[a-z0-9]\.pos\.108-61-190-4\.sslip\.io$" $ssl_server_name;
  default "none";
}
limit_req_zone  $binary_remote_addr zone=pos_auth:10m rate=10r/m;
limit_req_zone  $binary_remote_addr zone=pos_admin_auth:1m rate=5r/m;
limit_req_zone  $host zone=pos_host:10m rate=30r/s;
limit_conn_zone $host zone=pos_conn:1m;
server {                     # port 80, our names only (named server beats niura's default_server)
  listen 80;                 # copy niura's listen form exactly (IPv6 or not)
  server_name ~^[a-z0-9-]+\.pos\.108-61-190-4\.sslip\.io$;
  location = /.well-known/acme-challenge/pos-probe { default_type text/plain; return 200 "pos-ok\n"; }
  location ^~ /.well-known/acme-challenge/ { root /var/www/letsencrypt; }
  location / { return 301 https://$host$request_uri; }
}
server {                     # shops
  listen 443 ssl http2;
  server_name ~^[a-z0-9-]+\.pos\.108-61-190-4\.sslip\.io$;
  ssl_certificate     /etc/nginx/pos-certs/$pos_cert/fullchain.pem;
  ssl_certificate_key /etc/nginx/pos-certs/$pos_cert/privkey.pem;
  add_header Strict-Transport-Security "max-age=31536000" always;
  client_max_body_size 256k;
  limit_conn pos_conn 8;
  auth_basic "POS"; auth_basic_user_file /etc/nginx/.htpasswd-pos;   # pilot only, removed after the 401 sweep
  location ~ ^/api/auth/(login|password)$ { limit_req zone=pos_auth burst=5 nodelay; limit_req zone=pos_host burst=60 nodelay; include snippets/pos-proxy.conf; }
  location / { limit_req zone=pos_host burst=60 nodelay; include snippets/pos-proxy.conf; }
}
server {                     # admin: exact name beats the regex; same cert lines + HSTS
  listen 443 ssl http2;
  server_name admin.pos.108-61-190-4.sslip.io;
  auth_basic "POS admin"; auth_basic_user_file /etc/nginx/.htpasswd-pos-admin;
  location = /healthz { auth_basic off; proxy_set_header Host localhost; proxy_pass http://127.0.0.1:3401; }
  location ~ ^/api/admin/(auth|step-up) { limit_req zone=pos_admin_auth burst=3 nodelay; include snippets/pos-proxy.conf; }
  location / { include snippets/pos-proxy.conf; }
}
```

- **المقطع `snippets/pos-proxy.conf`** يضبط `proxy_pass http://127.0.0.1:3401`، و`proxy_http_version 1.1`، و`Host $host`، و`X-Forwarded-For $remote_addr`، و`X-Forwarded-Proto https`، و`X-Forwarded-Host ""`، و`Forwarded ""`، و`X-Request-Id $request_id`، و`proxy_read_timeout 60s`.
- **لماذا متغير للشهادة:** المسار المتغير يجعل `nginx -t` ينجح قبل وجود ملفات الشهادة، ويقرأ nginx الملفات عند كل مصافحة، فلا يحتاج إعادة تحميل عند إصدار أو تجديد.
- **ما يُمنع في هذا الملف:** `default_server` و`reuseport` و`ssl_session_cache`.
- **خطوات النشر:**
  1. أرشفة `/etc/nginx` إلى `/root/backups`.
  2. التأكد بـ `grep -rn pos_ /etc/nginx` أن الأسماء غير مستخدمة.
  3. `nginx -t`، ثم `reload`.
  4. فحص كل المواقع الأخرى.
  5. التراجع عند اللزوم: حذف الرابط الرمزي، ثم `nginx -t`، ثم `reload`.

**الشهادات (العامل `pos-root-worker`):**
- **الإعداد:**
  - certbot بمجلدات مستقلة: `--config-dir /etc/letsencrypt-pos` و`--work-dir` و`--logs-dir`. هذا يعطينا حسابًا وحدودًا خاصة بنا ولا يتعارض مع قفل niura.
  - تسجيل الحساب مرة واحدة بـ `certbot register`.
  - تجربة كاملة على بيئة `--staging` قبل الإنتاج.
- **مجلد الطلبات:**
  - `/var/lib/pos-spool` مملوك لـ `root:root` بالصلاحيات 0755.
  - المجلدات `desired/` و`retire/` و`requests/` مملوكة لـ `root:pos` بالصلاحيات 1730 (sticky).
  - `state/` مملوك لـ root، والتطبيق يقرؤه فقط. الكتابة فيه بملف مؤقت ثم `rename`، مع `O_NOFOLLOW`.
- **خطوات الإصدار:**
  1. يُفحص الاسم وأن الملف عادي.
  2. فحص DNS.
  3. فحص `pos-probe`، لتوفير حد «5 إخفاقات لكل اسم في الساعة».
  4. تشغيل `certbot certonly --webroot -w /var/www/letsencrypt`.
  5. خطّاف التثبيت يتأكد أن في الشهادة اسمًا واحدًا مطابقًا، ثم يثبّتها في `/etc/nginx/pos-certs/.<host>.<ts>/` ويبدّل الرابط الرمزي ذريًا، بنفس ملكية `niura-certs` وصلاحياتها.
- **الحدود والتجديد:**
  - 3 شهادات لكل تشغيل، و15 في اليوم.
  - انتظار متزايد بين المحاولات: دقيقتان، 10 دقائق، ساعة، 6 ساعات، 24 ساعة. بعد 6 محاولات تصبح الحالة `failed`.
  - التجديد مرتين يوميًا بـ `certbot renew` بنفس المجلدات. التجديد معفى من حد النطاق.
  - لا إبطال للشهادات (revocation) عند حذف متجر.
- **ما يراه المستخدم أثناء التجهيز:**
  - اللوحة تعرض «جارٍ تجهيز المتجر…»، وعادة يستغرق ذلك أقل من دقيقتين.
  - رابط المتجر وبيانات الدخول لا تظهر إلا بعد `issued`، لأن العنوان قبلها يفشل في مصافحة TLS.
  - لا يوجد رجوع إلى HTTP، لأن ماسح الكاميرا يحتاج سياقًا آمنًا.
  - عند الفشل تظهر «تعذّر إصدار شهادة الأمان» مع زر «إعادة المحاولة».
- **شهادة لوحة الإدارة:** تُطلب يدويًا مرة واحدة بإنشاء ملف `desired/admin.pos…`، ويُتحقق منها بـ `openssl s_client`، ثم يُشغَّل `create-admin`.

**العملية:**
- **وحدة systemd `pos.service`:**
  - `User=pos`.
  - `ExecStart=/opt/node-v24/bin/node --max-old-space-size=180 --env-file=/etc/pos/pos.env /srv/pos/current/server.js`. تُستخدم `/opt/node-v24` إذا اتضح أن Node الحالي مثبت تحت `/root`.
  - `MemoryHigh=220M`، `MemoryMax=280M`، `OOMScoreAdjust=800` على وحدتنا فقط.
  - `NoNewPrivileges`، `ProtectSystem=strict`، `ProtectHome`، `PrivateTmp`.
  - `ReadWritePaths` على مجلدات الطلبات فقط، و`Restart=always`، والسجلات في journald.
- **النشر بواسطة root:**
  1. `git fetch` في `/srv/pos/repo`.
  2. `git archive <sha>` إلى `releases/<sha>`.
  3. `npm ci --omit=dev`.
  4. أخذ dump لـ `pos_control`.
  5. `ln -sfn` إلى `current`.
  6. `systemctl restart pos`.
  7. انتظار `/readyz` حتى يعيد الـ sha الجديد.
- **التراجع:** إعادة الرابط الرمزي إلى الإصدار السابق. تُحفظ آخر 5 إصدارات.
- **وقت النشر:** خارج ساعات العمل. التوقف ثانية إلى ثلاث، وإعادة المحاولة بنفس `clientSaleId` تمنع البيع المكرر.

**السعة على 2 GB:**
- **المتاح الآن:** نحو 1.2 GB مستخدمة ونحو 800 MB متاحة. ذاكرة WiredTiger المؤقتة قد تنمو حتى نحو 512 MB، وهي مشتركة بين كل التطبيقات.
- **الهامش الحقيقي** = `MemAvailable` − (أقصى ذاكرة WT − الحالية) − 150 MB احتياطًا. يُقاس في المرحلة 0، وتُضبط عليه قيم `MemoryMax`.
- **عدد الملفات:** كل متجر يضيف نحو 40 ملف WiredTiger، فعشرون متجرًا تضيف نحو 800 ملف إلى الأربعمئة الحالية.
- **الحد على هذا الخادم:** **20 متجرًا**. لا يُرفع إلا بعد قياس `bench-tenants` بـ 30 و60 و100 متجر على الخادم التجريبي، وليس على `mongod` الإنتاجي أبدًا.
- **التنبيهات:** عندما يقل `MemAvailable` عن 300 MB، أو يتجاوز امتلاء القرص 80%.

**النسخ والاستعادة:**
- **النسخ الليلي:**
  - الوحدة `pos-backup.timer` تعمل كـ root في `03:30 Asia/Baghdad`، مع `Persistent=true` و`Nice=10` وأولوية إدخال وإخراج منخفضة (`IOSchedulingClass=idle`) و`UMask=0077`.
  - ينفّذ `mongodump --db=<db> --gzip --archive` لـ `pos_control` ولكل قاعدة مسجلة فيه، إلى `/var/backups/pos` المملوك لـ root بالصلاحيات 0700.
  - الاحتفاظ: 14 نسخة يومية، و8 أسبوعية، و6 شهرية.
  - نسخة خارج الخادم عبر restic مشفّر، بمفتاح لا يملك صلاحية الحذف، مع إشعار عند انتهاء النسخ.
  - كل أسبوع تُستعاد نسخة متجر واحد تلقائيًا إلى قاعدة مؤقتة وتُقارن أعداد السجلات.
- **قيد معروف:** نسخة القاعدة الواحدة على خادم MongoDB مستقل (standalone) ليست لقطة لحظية دقيقة، لذلك تُؤخذ في ساعة هادئة.
- **الاستعادة:**
  1. يُطلب من العامل استعادة النسخة إلى قاعدة جديدة `pos_t_<ObjectId جديد>`.
  2. تُقارن الأعداد وإجماليات الملخص.
  3. يُوقف المتجر، وتُحذف جلساته، وتُنسخ مجموعة `users` الحالية إلى القاعدة المستعادة.
  4. `switchDb()`.
  5. تُحفظ القاعدة السابقة 7 أيام.
  6. يُستأنف المتجر.

**المراقبة:**
- **`/readyz`** يفحص الاتصال بقاعدة التحكم، ويعيد الـ sha وتأخر حلقة الأحداث. يُرسل تنبيه إذا زادت قيمة p99 عن 200 ms.
- **`pos-monitor.timer`** يعمل كل 5 دقائق ويفحص:
  - الذاكرة والقرص، وعمل `mongod`؛
  - أخطاء 5xx، والشهادات التي ينتهي أجلها خلال 14 يومًا، وإخفاقات العامل؛
  - آخر نسخة احتياطية أقدم من 26 ساعة.
- التنبيهات عبر تلغرام، بتنبيه واحد على الأكثر لكل حالة في الساعة، مع فحص خارجي مجاني لـ `admin…/healthz`.
- السجلات سطر JSON لكل طلب، فيه `{tenant, reqId, route, status, ms}`، دون محتوى الطلب أبدًا.

| حالة طارئة | ما يراه المستخدم | المعالجة |
|---|---|---|
| انقطاع الاتصال أثناء الدفع | رسالة مع زر «إعادة المحاولة»، والسلة باقية | إعادة الإرسال بنفس `clientSaleId` |
| انتهاء الجلسة أو إيقاف المتجر أثناء البيع | نافذة دخول داخل الصفحة، أو شريط إيقاف | السلة لا تضيع |
| تعطل DNS الخاص بـ sslip.io | الموقع لا يفتح | التنبيه الخارجي. الحل الدائم هو النطاق الحقيقي |
| البيع دون اتصال | غير مدعوم في المرحلة الأولى | مشروع منفصل لاحقًا |

**الانتقال من النظام الحالي والتراجع:**
- **الانتقال:**
  1. إنشاء متجر `smoke` فارغ. لن تُستعاد النسخة المؤرشفة إلا إذا طلبت ذلك، وعندها تُستعاد إلى المتجر قبل أول بيع، مع `--dryRun` أولًا.
  2. تحويل `smoke.108-61-190-4.sslip.io` بـ `return 302` لمدة أسبوعين، ثم 301.
  3. `pm2 stop smoke-shop && pm2 save`، مع إبقاء التطبيق مثبتًا 30 يومًا.
- **التراجع بالترتيب:**
  1. إيقاف المؤقتات الثلاثة و`pos.service`.
  2. حذف رابط `sites-enabled/pos`، ثم `nginx -t && reload`.
  3. استعادة ملف موقع smoke من أرشيف nginx.
  4. `pm2 restart smoke-shop`.
  5. إعادة البيانات بـ `mongodump --db pos_t_<id> --archive | mongorestore --archive --nsFrom 'pos_t_<id>.*' --nsTo 'smoke_shop.*'`، مع استثناء `users` و`settings`. أسماء المجموعات لم تتغير، فيقرؤها الكود القديم كما هي.

## 8. لوحة الأدمن ودورة حياة المتجر

**الشاشات** (عربية من اليمين لليسار، وتعيد استخدام `style.css` ومكونات `.ptable` و`.chips` و`.badge` و`dialog`):

1. **دخول المسؤول:** نافذة basic auth، ثم اسم المستخدم وكلمة المرور، ثم «رمز التحقق»، مع رابط «استخدم رمزًا احتياطيًا».
2. **المتاجر:**
   - زر «متجر جديد»، وبحث بالاسم أو العنوان.
   - رقائق تصفية: الكل، نشط، قيد التجهيز، موقوف، بانتظار الحذف.
   - الأعمدة: الاسم (التسمية التي أدخلتها أولًا، وتحتها اسم المتجر الذي كتبه صاحبه كنص ثانوي)، العنوان من اليسار لليمين، الحالة، الفواتير، حجم البيانات، آخر نشاط، الشهادة.
3. **متجر جديد** (يتطلب التأكيد الإضافي، ويحمل `requestId` حتى لا يتكرر):
   - الحقول: التسمية، واسم المتجر على الإيصال، والعنوان مع اللاحقة الثابتة.
   - فحص العنوان مباشرة أثناء الكتابة بعد 300 ms من التوقف، ويعرض: «متاح»، أو «مستخدم»، أو «محجوز»، أو «غير صالح: أحرف إنجليزية صغيرة وأرقام وشرطة، يبدأ بحرف، من 3 إلى 30».
   - المنطقة الزمنية، والعملة، واسم مستخدم المالك، وكلمة مرور تُولَّد في المتصفح (12 حرفًا مقروءة) مع زر نسخ، والهاتف، والملاحظات، ورقم بداية الفواتير (اختياري، والافتراضي 1).
4. **تقدّم التجهيز:** قائمة تتحدث كل ثانيتين: قاعدة البيانات ← الفهارس ← الإعدادات وقسم «عام» ← حساب المالك ← فحص DNS ← شهادة الأمان ← جاهز.
   - الخطوة الفاشلة تظهر بالأحمر مع زر «إعادة المحاولة».
   - في النهاية تظهر بطاقة فيها العنوان واسم المستخدم وكلمة المرور، مأخوذة من ذاكرة المتصفح وليست مخزنة على الخادم، مع زر «نسخ الكل».
5. **تفاصيل المتجر:**
   - المعلومات.
   - الإعدادات: تُعدَّل وثيقة `settings` في قاعدة المتجر، ويُحدَّث `shopNameCache`.
   - حسابات الدخول: «إعادة تعيين كلمة المرور» تولّد كلمة جديدة وتلغي الجلسات.
   - الجلسات النشطة، مع «إلغاء كل الجلسات».
   - النسخ الاحتياطية: القائمة و«نسخة الآن».
   - منطقة الخطر: إيقاف أو استئناف، وتغيير العنوان والحذف (في المرحلة 7).
6. **سجل العمليات:** الأعمدة الوقت، والعملية بتسمية عربية، والمتجر، والتفاصيل، وعنوان IP. تصفية حسب المتجر والعملية، و50 سطرًا في الصفحة.

**الحالات:** كل انتقال بين الحالات يمر عبر `transition(id, from, to)`، وهي:
- تحدّث الحالة فقط إذا كانت الحالة الحالية هي `from` (compare-and-set)،
- تزيد `rev`،
- تلغي الجلسات عند الخروج من حالة `active`،
- تكتب في السجل.

| الحالة | ما يظهر على عنوان المتجر | ما يمكنك فعله |
|---|---|---|
| `provisioning` | الحالة 503 مع «جارٍ تجهيز المتجر» | المتابعة، إعادة محاولة خطوة، الإلغاء |
| `active` | الاستخدام الكامل | التعديل، إعادة التعيين، النسخ، الإيقاف، تغيير العنوان، الحذف |
| `suspended` | الحالة 423 `TENANT_SUSPENDED` مع «هذا المتجر موقوف مؤقتًا، تواصل مع الإدارة». تظهر شريطًا في الصفحة دون فقد السلة | الاستئناف، النسخ، الاستعادة، الحذف |
| `pending_deletion` | نفس رسالة الإيقاف | إلغاء الحذف (يعود إلى موقوف) |
| `deleted` | الحالة 410 مع «هذا المتجر لم يعد موجودًا» | استعادة النسخة الأخيرة كمتجر جديد |

أي عنوان مجهول أو محجوز يعطي 404.

**تغيير العنوان (مهمة):**
1. فحص DNS للعنوان الجديد.
2. إصدار شهادته.
3. جعله العنوان الأساسي.
4. تحويل العنوان القديم إلى عنوان توجيه لمدة 90 يومًا: صفحات HTML تُحوَّل بـ 301، وطلبات `/api` تعيد 410 `TENANT_MOVED` مع العنوان الجديد، فتظهر رسالة «تم نقل المتجر إلى عنوان جديد» دون فقد السلة.
5. بعد ذلك يُعلَّم القديم `retired`.

نافذة التأكيد تنبّه إلى ثلاثة أمور: الجميع سيحتاج تسجيل الدخول من جديد، ومسودة الشراء وترتيب المنتجات المحفوظان في المتصفح سيضيعان، والإشارات المرجعية تعمل خلال مهلة التوجيه فقط.

**الحذف:**
1. تكتب عنوان المتجر وتدخل الرمز.
2. العامل يأخذ نسخة احتياطية ويتحقق منها: الملف غير فارغ ويمكن سرد محتواه.
3. تصبح الحالة `pending_deletion`، ويُحدَّد `purgeAfter` بعد 30 يومًا. خلال المهلة يُمنع الدخول.
4. بعد المهلة تؤخذ نسخة نهائية ويُتحقق منها، ثم يحذف العامل القاعدة.
5. تُعلَّم العناوين `retired`، وتُحذف الشهادات بعد 24 ساعة.
6. يُحفظ الأرشيف 12 شهرًا.

«الحذف النهائي الآن» متاح فقط من سطر الأوامر على الخادم (`scripts/tenant-purge.js --slug x --confirm`).

## 10. المخاطر والتخفيف

| الخطر | التخفيف |

| نفاد الذاكرة على الخادم المشترك، وأكبر ضحية محتملة هي `mongod` فتتوقف كل المواقع | عملية واحدة بحدود `MemoryMax` و`OOMScoreAdjust`، وحد 20 متجرًا، وتنبيه عند 300 MB، والقياس قبل رفع الحد |

| حدود Let's Encrypt على sslip.io (حد مشترك عالميًا) | حدود ذاتية وانتظار متزايد وفحص مسبق وبيئة staging. المتاجر القائمة تبقى تجدد شهاداتها لأن التجديد معفى |

## 11. أسئلة تحتاج قرارك قبل البدء

1. **هل «يوزر» عندك يعني متجرًا مستقلًا كاملًا** (قاعدة بيانات وعنوان وحساب لصاحبه)، و«حساب الدخول» شيء منفصل داخل المتجر؟
   الموصى به: نعم، وبهذه التسميات في الواجهة.
2. **أين ستعمل المتاجر الخارجية؟**
   الموصى به: خادم صغير مستقل للمتاجر بنطاق حقيقي، وMongoDB فيه بمصادقة من البداية. البديل هو تفعيل المصادقة على الخادم الحالي، وهذا يعني تعديل hishin وlapsa وniura وsales-accounts وurgold وإعادة تشغيلها.
3. **النطاق الحقيقي:** متى نشتريه، وبأي اسم؟
   الموصى به: نبقى على sslip.io لمتجرك وللتجارب، ونشتري النطاق (نحو 12 دولارًا في السنة، عند مزود له API مثل Cloudflare) قبل أول متجر خارجي.
4. **عنوان متجرك:** هل نبقي `smoke.pos…`، علمًا أن العناوين لا يُعاد استخدامها؟ وهل نستعيد بيانات الأرشيف المحذوفة؟
   الموصى به: `smoke`، وبلا استعادة، لأنك طلبت المسح.
5. **إذا كانت نسخ hishin الليلية تشمل كل القواعد:** هل نستثني منها `pos_*` (تعديل صغير على hishin بموافقتك)، أم نتركها ونوثّق ذلك؟
   الموصى به: الاستثناء.
6. **التنبيهات والنسخ خارج الخادم:** هل نستخدم بوت تلغرام للتنبيهات، وBackblaze B2 أو Vultr Object Storage للنسخ (تكلفة شهرية بسيطة)؟
   الموصى به: نعم للاثنين.
7. **كلمة المرور الأولى:** هل نعتمد كلمة مرور مولّدة تُرسل بواتساب ويُفرض تغييرها عند أول دخول، ونؤجل روابط التفعيل؟
   الموصى به: نعم.
8. **القيم الافتراضية للمتجر الجديد:** المنطقة الزمنية `Asia/Baghdad`، والعملة `د.ع`، وقسم «عام»، والفواتير تبدأ من 1 مع إمكانية تغييرها، ودور المالك فقط دون كاشير في المرحلة الأولى.
   الموصى به: نعم.
